## 1. Context

Slydr is a locally running, browser-based slide-show application made of a Node.js/Express 5
API (`server/`), a Vite + React 19 single-page client (`client/`), and a small package of
shared types and constants (`shared/`). All three live in a single Git repository managed
with npm workspaces and written in TypeScript as native ES modules.

This ticket creates the empty skeleton that every other ticket builds on: the root
`package.json`, the shared TypeScript base configuration, the three workspace packages with
their own manifests and `tsconfig.json` files, the ignore files, the Node version pin, and
the first Git commit. It also declares every third-party dependency the project will need,
so later tickets never have to touch the dependency graph just to start work. No application
logic is written here; the root scripts from specification §13.1 exist but are stubs that
fail loudly until the ticket that owns them replaces them.

Notes on the scripts:

- **`build` is real from day one.** It builds `@slydr/shared` first (the other packages
  consume its compiled output, see §4.5), then `@slydr/server`, then `@slydr/client` only if
  that workspace defines a `build` script (`--if-present`; the client has none until epic
  E9). The explicit `&&` chain is used instead of `npm run build --workspaces` so the order
  is deterministic and does not depend on npm's workspace iteration order. `&&` in an npm
  script works under both `cmd.exe` and POSIX shells.
  T002 prepends a `typecheck` step to match §13.1 ("typecheck, build shared, build client,
  compile server"); it cannot be added here because `typecheck` is still a stub.
- **Every other script is a loud stub.** A stub must never exit 0, because a silent pass would
  let CI go green on code that checks nothing. Each stub runs
  `scripts/not-implemented.mjs` (below); the trailing arguments after the script name are the
  ticket or epic identifiers that will replace it.
- No script uses shell-specific syntax (no `$VAR`, no `&` backgrounding, no `rm`/`cp`),
  because the developer machine is Windows and CI also runs on macOS and Linux.
- No `postinstall` or `prepare` script. *Decision (not specified):* installation must have no
  side effects, so that the CI step in T003 which inspects the install log for compiler
  activity sees only what npm itself does.

#### The no-compiler rule (§2.3)

> No dependency may require a compiler toolchain at install time on any of the three
> platforms.

This is a hard constraint on every dependency ever added, not only today's list. Rules for
this ticket and for reviewers of later tickets:

1. A package that needs `node-gyp`, `node-pre-gyp`, `cmake-js`, Python, Visual Studio Build
   Tools or Xcode command-line tools to install is forbidden.
2. `sharp` satisfies the rule because since 0.33 it ships its native code in per-platform
   optional packages (`@img/sharp-win32-x64`, `@img/sharp-darwin-arm64`,
   `@img/sharp-linux-x64`, and so on) that npm selects by `os`/`cpu` and downloads as
   ordinary tarballs. There is no install script and no compile step. Do not add
   `sharp` install flags or environment variables such as `SHARP_IGNORE_GLOBAL_LIBVIPS`.
3. Verification in this ticket (run after `npm install`, see §5):
   - `node -e "import('sharp').then(m => m.default({create:{width:4,height:4,channels:3,background:'#fff'}}).png().toBuffer()).then(b => console.log('sharp ok', b.length))"`
     prints `sharp ok` followed by a number.
   - Search `package-lock.json` for `"hasInstallScript": true`. Every package carrying that
     flag must be reviewed. The expected set is `esbuild` (its postinstall only verifies an
     already-downloaded binary and compiles nothing). Anything else must be explained in the
     commit message or removed.
   - Search `package-lock.json` for the strings `node-gyp` and `prebuild-install`; neither
     may appear as a dependency of any package that is actually installed.
4. The automated, per-OS version of this check is added to CI by **T003**; it is a release
   blocker per §12.5.

### 4.4 TypeScript configuration

#### `tsconfig.base.json` (repo root)

```json
{
  "compilerOptions": {
    "target": "ES2023",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "sourceMap": true
  }
}
```

The base file deliberately does **not** set `module`, `moduleResolution`, `lib` or `types`;
those differ by package and each package states them explicitly so a reader sees the choice
in the file that it affects.

- `target: ES2023` is fully supported by Node 22 and by every browser that supports the
  features the spec requires (View Transitions are not used; `img.decode()`, `inset` and
  `100dvh` are).
- `strict: true` is required by the specification ("TypeScript throughout"; T008 assumes
  strict mode).
- `verbatimModuleSyntax: true` means type-only imports must be written `import type { X }`.
  It keeps emitted ESM predictable and works identically under `tsc`, `tsx`, Vite and
  Vitest. *Decision (not specified).*
- `noUncheckedIndexedAccess: true` makes `array[i]` and `record[key]` return `T | undefined`.
  Path-segment handling in the jail and the scanner is exactly the code where an unchecked
  index is a security bug. *Decision (not specified).*

#### `moduleResolution` per package, and why

| Package | `module` | `moduleResolution` | Reason |
|---|---|---|---|
| `shared` | `NodeNext` | `NodeNext` | Compiled with `tsc` and executed by Node unbundled (the server imports it at runtime). TypeScript must enforce the same rules Node's ESM loader enforces: explicit `.js` extensions on relative imports, `exports` maps, no directory imports. The emitted files are also valid input for Vite's bundler. |
| `server` | `NodeNext` | `NodeNext` | Compiled with `tsc` to `server/dist` and run by plain `node`. In development `tsx` runs the TypeScript directly but follows the same resolution. |
| `client` | `ESNext` | `bundler` | Vite resolves and bundles modules, so extensionless relative imports (`'./App'`) and `.tsx` imports are legal and idiomatic. `NodeNext` would force `.js` suffixes on every import of a `.tsx` file, which is noise with no benefit in a bundled app. |

Consequence the implementer must remember: in `shared/src` and `server/src`, relative
imports **must** carry a `.js` extension even though the file on disk is `.ts`
(for example `import { createApp } from './app.js'`). In `client/src` they must not.

#### Project references and `composite`: decision

*Decision (not specified):* **do not use `composite` or TypeScript project references.**
Reasons: (a) `tsc -b` and `--noEmit` do not combine cleanly, and §13.1 defines
`typecheck` as `tsc --noEmit` across workspaces; (b) with only three small packages the
incremental-build benefit is negligible; (c) the `client` is built by Vite, not `tsc`, so it
cannot be a normal participant in a reference graph. Instead the dependency order is
enforced by scripts: `shared` is always built first and `server`/`client` resolve
`@slydr/shared` through its compiled `dist/` output (see §4.5). Do not set `composite`,
`incremental`, `references`, or `tsBuildInfoFile` anywhere.

### 4.5 `@slydr/shared`: no runtime dependencies, and how it is consumed

**Rule.** `shared/package.json` must contain no `dependencies`, `peerDependencies` or
`optionalDependencies`. It is pure TypeScript: types, constants and small pure functions.
This keeps the client bundle free of anything accidental and lets the server import it
without pulling extra code. Any ticket that wants to add a dependency to `shared` must be
rejected or redesigned.

**Consumption decision (labelled).** *Decision (not specified):* **`server` and `client`
consume `@slydr/shared` through its compiled build output (`shared/dist`), reached via the
workspace symlink — not through its TypeScript source.**

Rationale:

- The production server runs compiled JavaScript with plain `node`; Node 22 cannot execute
  `.ts` files from `node_modules` without flags, so `shared` must be compiled for the server
  anyway. Using the same artefact everywhere removes a class of "works in dev, fails in
  production" differences.
- With `moduleResolution: NodeNext` a source-level import would require custom `exports`
  conditions and `customConditions` in every consumer. A plain `dist` export is simpler and
  well understood by `tsc`, `tsx`, Vite and Vitest.
- The cost is that `shared` must be built before anything that imports it is type-checked or
  tested. That ordering is handled in scripts, not by developers remembering it:
  the root `build` script builds `shared` first (this ticket); T002 makes `typecheck` and
  `test` build `shared` first; T019 makes `npm run dev` run `tsc -p shared/tsconfig.build.json
  --watch` alongside the server and Vite (without it, edits to `shared/src` would not reach
  the running server or client).

`shared/package.json`:

```json
{
  "name": "@slydr/shared",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "description": "Shared types, constants and pure helpers for Slydr. No runtime dependencies.",
  "sideEffects": false,
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
```

### 4.6 `scripts/not-implemented.mjs`

```js
// Stub used by root npm scripts that are not implemented yet.
// It must fail loudly: a stub that exits 0 would let CI pass while checking nothing.
// Usage: node scripts/not-implemented.mjs <script-name> [<owning ticket or epic> ...]
const [name = '(unknown)', ...owners] = process.argv.slice(2);
const owner = owners.length > 0 ? owners.join(', ') : 'a later ticket';
console.error(`[slydr] "npm run ${name}" is not implemented yet (owned by: ${owner}).`);
console.error('[slydr] This stub fails on purpose so an unimplemented step cannot pass silently.');
process.exit(1);
```

The script is plain ESM JavaScript (root `"type": "module"`), uses no platform-specific API,
and is invoked as `node scripts/not-implemented.mjs ...` from npm scripts, which npm runs
with the repository root as the working directory on every OS.

When a later ticket implements a script, it replaces that script's value in the root
`package.json`. When the last stub is gone, delete `scripts/not-implemented.mjs` in the same
change.

### 4.8 `.gitattributes`

```gitattributes
* text=auto eol=lf
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary

```

*Decision (not specified):* force LF line endings in the working tree. The developer machine
is Windows, where Git's default `core.autocrlf` would otherwise check files out with CRLF,
and Prettier (configured with `endOfLine: "lf"` in T002) would then report every file as
unformatted on Windows while passing on macOS and Linux. Do not change Git config to fix
this; the attributes file is the repo-local, portable fix.

### 4.9 `.nvmrc`

The file contains the single line:

```
22
```

*Decision (not specified):* pin the minimum supported major (22), not the developer's own 24,
so that a contributor who follows `.nvmrc` develops on the floor of the supported range. CI
(T003) tests both 22 and 24. Note that Vite 7 itself requires Node `^20.19.0 || >=22.12.0`,
so within the 22 line use 22.12 or newer; `nvm use` with `22` installs the latest 22.x, which
satisfies this.

## 8. Notes and gotchas

- **Stubs failing is the feature.** It is expected and correct that most root scripts exit
  non-zero after this ticket. Do not "fix" them by making them exit 0; tickets T002, T019
  and T039 replace them.
- **Relative import extensions.** In `shared/src` and `server/src` an import of `./app` fails
  under `NodeNext`; it must be `./app.js`. In `client/src` the opposite holds. Mixing these up
  is the most common first-day error in this layout.
- **`shared` must be built before consumers see it.** A fresh clone has no `shared/dist`, so
  `tsc -p server/tsconfig.json` reports "Cannot find module '@slydr/shared'" until
  `npm run build -w @slydr/shared` has run. This is expected; T002 automates the ordering for
  `typecheck` and `test`.
- **Vite 7's Node floor.** `engines.node` in the spec is `>=22`, but Vite 7 needs 22.12 or
  newer inside that line. This is why CI uses the latest 22.x and why `.nvmrc` says `22`
  rather than a pinned patch.
- **Do not add `sharp` flags.** Some guides recommend `npm install --include=optional` or
  `--os`/`--cpu` flags. They are not needed for a normal single-platform install, and
  `--omit=optional` would break `sharp` entirely.
- **`lucide-react` is `0.x`.** Its minor version changes can rename icons. The `^0.544.0`
  range keeps patch updates only; bumping the minor is a deliberate act.
- **Open items from §16.2** do not affect this ticket. The default port (4317) is not
  referenced anywhere here.
