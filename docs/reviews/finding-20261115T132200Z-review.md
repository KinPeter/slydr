## Findings

A `publicDir` change (see `client/vite.config.ts`, tested in `client/test/vite-config.test.ts`) or a deleted asset would silently fall back to the 204 handler while `client/test/favicon.test.ts` (which reads `client/public` directly) and `server/test/static.test.ts` (which writes its own fixture) both still pass. Extend the existing `describe.skipIf(!fs.existsSync(indexPath))` block to assert `favicon.ico`, `favicon-32x32.png` and `site.webmanifest` exist in `dist` when the client is built.
- MINOR: `client/public/site.webmanifest:2-3,8-9` is now referenced from `client/index.html:25` but declares an empty `name`/`short_name` and hard-coded `#ffffff` theme/background colours, which is inconsistent with the app's token-based theming (`client/src/styles/tokens.css`) and with the "Slydr" name fixed in `tasks/README.md` "UI name contract". The asset was supplied by the user, so this is optional; if the manifest is to stay linked, setting `"name": "Slydr"` / `"short_name": "Slydr"` and a theme colour matching the tokens is the minimal fix.
